## Scope
- Finishes already implemented work by running the full suite, identifying workspace and base, and asking how to integrate.
- Includes local merge and merged-tree tests, push/PR creation, keep-as-is, explicit discard and provenance-aware cleanup.
- Ends at a tested local merge with eligible workspace/branch cleanup, a reported PR URL with workspace retained, or an explicitly preserved/discarded branch.
- Does not implement features, conduct code review, deploy or manage releases.

## Findings

### Needed
None. Integration and cleanup have substantive tests and human gates; the gaps below are partial coverage or contextual safeguards, not missing end-to-end stages.

### Worth considering
1. **Check that the tested work is the work Git will integrate** [model+map+trace]
   Map node: version-control.version-control — source: DORA capabilities catalog, Version control <https://dora.dev/capabilities/>.
   Why: Step 1 tests the working tree, but merge/push consumes commits; the only dirty-state check comes after cleanup refuses removal. Since completed implementation may already be committed and cleanup protects uncommitted files, this is a preflight improvement rather than wholly absent state protection.
   Fix: before tests, inspect branch, staged/unstaged changes and untracked files; resolve which work is intended for integration and verify the resulting committed tree.
2. **Explain conflict handling and local recovery** [model+map+trace]
   Map node: version-control.integrate-and-merge, version-control.revert — source: GitHub Docs, Resolve merge conflicts and Revert a pull request <https://docs.github.com/en/pull-requests>.
   Why: Step 5 merges, tests and stops on failure, but does not describe conflicts or how to restore the pre-merge state safely. Stop-and-preserve is meaningful partial coverage; automatic rollback is not required.
   Fix: in Option 1, distinguish merge-command failure from merged-test failure, preserve evidence, and identify the safe recovery/escalation path without discarding unrelated work.
3. **Give PR descriptions and reviewer routing a fallback** [model+map]
   Map node: review.pull-request, version-control.change-description — source: GitHub Docs, Request a PR review <https://docs.github.com/en/pull-requests>; Google Engineering Practices, Writing good CL descriptions: Review the description before submitting the CL <https://google.github.io/eng-practices/>.
   Why: Option 2 follows an existing PR template and conventions, but says nothing about description contents or requesting reviewers when those are absent. Review execution and final approval remain outside this skill's boundary.
   Fix: in Option 2, add fallback what/why/test-evidence fields, a description check and reviewer selection according to repository policy.
4. **Check publication contents, not just permission to push** [model+map]
   Map node: implementation.secrets, agent.sensitive-data — source: GitHub Docs, Secret scanning: Push protection <https://docs.github.com/en/pull-requests>; OWASP Top 10 for LLM Applications 2025, LLM02:2025 Sensitive Information Disclosure <https://genai.owasp.org/llm-top-10/>.
   Why: permission to push is explicit, but Option 2 never checks the outgoing commits for credentials or unintended private material. This is contextual defence in depth for already implemented work, especially when repository push protection is unavailable.
   Fix: before Option 2 pushes, inspect the outgoing range for unintended sensitive files and apply the repository's secret-checking policy.
5. **Keep repository text from becoming operational authority** [map]
   Map node: agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01:2025 Prompt Injection <https://genai.owasp.org/llm-top-10/>.
   Why: Option 2 reads repository templates and conventions without distinguishing formatting guidance from instructions to execute additional operations. The concern depends on whether repository content is trusted, rather than an unavoidable exposure in every finishing session.
   Fix: in Option 2, constrain template use to PR content and preserve the user's explicit integration permissions.

### Minor
6. **Handle branch occupancy and tool failure before cleanup** [model+trace] (unsourced)
   Why: Step 2 detects normal/named/detached environments but not a base branch checked out in another worktree; checkout, pull or PR creation can also fail without a specific continuation rule. The commands must not be treated as successful merely because tests passed earlier.
   Fix: in Step 5, check each command result, stop on failure and report the retained workspace and actual remote/PR state.
7. **Do not infer ownership from directory names alone** [model+trace] (unsourced)
   Why: Step 6 treats the worktree directory prefix as provenance, although another tool or user can create a clean worktree there. Non-forced removal protects uncommitted files, but not the user's expectation that an externally created workspace stays available.
   Fix: in Steps 2 and 6, use recorded creation provenance or confirm ownership before removing a worktree identified only by its directory name.
