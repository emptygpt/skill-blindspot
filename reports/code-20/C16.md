## Scope
- Iterates an existing current-branch PR through actionable CI failures and high/medium review feedback, asking about low-priority items.
- Fetches PR/check/review state, investigates causes and related instances, implements fixes, verifies locally, commits/pushes and monitors the next CI/feedback cycle.
- Ends at actionable checks passing plus a delayed clean feedback check and handled low-priority choice, or a reported no-PR/no-check/draft/human-gate/rebase/infrastructure/repeated-failure stop.
- Does not create the PR, mark drafts ready without request, merge/rebase without direction, deploy or wait for human merge approval. CI monitoring/logs are not production observability work.

## Findings

### Needed
None. Root-cause verification, targeted local checks, repeated CI/feedback acquisition, explicit infrastructure escalation and CLI fallback are real partial safeguards for state/coverage gaps. Input-trust and sensitive-data concerns depend on who controls the feedback and what the target exposes.

### Worth considering
1. **Bind a clean feedback/CI decision to complete data and the current head** [model+map+trace]
   Map node: agent.wrong-output, review.handle-comments, version-control.version-control — source: OWASP LLM09 <https://genai.owasp.org/llm-top-10/>; Google Engineering Practices, How to handle reviewer comments <https://google.github.io/eng-practices/>; DORA, Version control <https://dora.dev/capabilities/>.
   Why: Local verification, post-push rechecks, delayed final feedback and a CLI fallback already provide partial protection. Helpers can return empty feedback lists after acquisition errors, inspect only the first 100 threads/first comment, and match failed runs by branch/workflow without checking the returned headSha, so a clean summary or failure snippet can omit or misattribute evidence.
   Fix: in fetch/check/feedback helpers and the final gate, retain acquisition completeness/errors and cursors, bind checks/logs/feedback to the current head, and require an explicit fallback or unknown/blocked outcome when that evidence is unavailable.

2. **Retain a small falsifiable regression check for each behavioral fix** [model+map+trace]
   Map node: testing.plan-strategy, testing.regression-and-negative, testing.reproduce-and-report — source: O*NET 31.0, tasks 14638 and 14640–14643 <https://www.onetcenter.org/database.html>; ESCO, replicate customer software issues/report test findings <https://esco.ec.europa.eu>.
   Why: Reading full failure logs, stating the cause, searching related code and running covering tests are substantive requirements. New focused coverage is conditional and the loop does not require observing a behavioral test fail before the fix or preserving relevant negative/related cases, so a passing old test can still miss the claimed correction.
   Fix: in feedback/CI fix steps, record the smallest failing behavior check and its red/green result when feasible, add relevant related/negative controls, and state a concrete reason when no such seam exists.

3. **Bound polling, publication and the runtime execution envelope** [model+map+trace]
   Map node: agent.limit-agency, agent.generated-code-execution, version-control.small-changes — source: OWASP LLM05/LLM06 <https://genai.owasp.org/llm-top-10/>; DORA, Working in small batches <https://dora.dev/capabilities/>; Google Engineering Practices, Small CLs <https://google.github.io/eng-practices/>.
   Why: The skill stops on repeated failures/rebase/human gates, verifies before push and offers a monitor timeout, so authority is not unbounded. The ordinary polling path still has no total deadline/push budget, the monitor retries transient errors indefinitely, and local tests/commands run with the caller's credentials without an explicit ownership/isolation check.
   Fix: at intake and before each commit/push, establish the current work's ownership, coherent change batch and permitted credentials/commands; bound elapsed polling and pushes and return unresolved infrastructure evidence rather than silently extending the loop.

4. **Keep external feedback/logs from acquiring tool authority or exposing sensitive values** [model+map+trace]
   Map node: agent.injected-instructions, agent.sensitive-data — source: OWASP LLM01/LLM02 <https://genai.owasp.org/llm-top-10/>; NIST AI 600-1, 2.4/2.9 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: Runtime instructions consume reviewer bodies, general PR conversation and CI logs, then authorize local changes and pushes without an instruction/data or output-redaction gate. The SPEC's forbidden-data policy expresses intent but is not a runtime read; this matters when commenters/log producers are untrusted or diagnostics contain private values, rather than establishing that any secret was exposed.
   Fix: in runtime feedback/log intake and replies, separate evidence from permission, verify the scope/authority of requested actions and minimise/redact sensitive content before returning or publishing it.

### Minor
5. **Carry the diagnosed cause into the commit message** [model+map+trace]
   Map node: version-control.commit-messages — source: Conventional Commits 1.0.0 <https://www.conventionalcommits.org/en/v1.0.0/>; Google Engineering Practices, First Line/Body is Informative <https://google.github.io/eng-practices/>.
   Why: The descriptive fix template and pre-edit cause statement convey intent locally. The commit itself need not retain why the change was necessary once that conversation is unavailable.
   Fix: extend the commit step with the repository's concise cause/rationale convention.

6. **Handle unfamiliar terminal check states explicitly** [model+trace] (unsourced)
   Why: monitor_pr_checks tests pending/fail and otherwise prints ALL_CHECKS_PASSED; canceled or unfamiliar buckets are not positively established as passed. Skipped/canceled checks can be legitimate, but the completion marker needs an explicit accepted-status policy rather than inference from the absence of two buckets.
   Fix: in terminal classification and its summary, distinguish passed, intentionally skipped/canceled and unknown/incomplete checks.

## Unsourced findings
- Finding 6 is a static model/trace candidate; no checked map source establishes the helper's precise terminal-marker classification.
- Finding 1's routes are statically present: main calls get_review_threads/get_issue_comments and their error paths return []; the defined REST inline-comment getter is not called as a fallback. No GitHub failure was induced.
- Late feedback/head changes, private data and malicious comment execution were not observed. No audited helper, gh call or repository command was executed.

| Investigate/fix | cause statement, related-site fix and optional focused tests → local verification | root cause required before edit; no universal observed-red/negative-case evidence |
| Verify/commit/push | local check results and descriptive fix commit → next remote cycle | local failures fixed before publication; no explicit preserved-user-edit/coherent-batch guard |
| Monitor/post-CI | new checks and delayed feedback snapshot → repeat/success/human-gate report | restart after each push, two-attempt escalation and CLI fallback; fetch completeness, total duration and unknown statuses need explicit handling |
| Optional thread reply | batched GraphQL reply results → caller/reviewer | JSON escaping, per-alias errors and timeout handled; reply authority/redaction left to caller |
| Exit | actionable green/clean feedback or named blocker → requester | no merge/approval bypass; final head/evidence identity and retained uncertainty could be explicit |
