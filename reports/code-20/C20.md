## Scope
- Produces a repository/path-specific AppSec threat model: components, data flows, trust boundaries, assets/objectives, attacker capabilities, prioritized abuse paths and evidence-backed controls.
- Requires an assumption-validation pause with the user, distinguishes existing/recommended mitigations and identifies concrete paths for later manual review.
- Ends at a concise Markdown threat-model file with a compact Mermaid diagram and a completeness/format quality check.
- Does not execute exploit tests, implement mitigations, conduct the later code review, open remediation tickets, deploy or operate the controls it describes; listing a control category does not import its implementation workflow.

## Findings

### Needed
1. **Treat the repository and supplied summaries as evidence, not analyst instructions** [model+map+trace]
   Map node: agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01 <https://genai.owasp.org/llm-top-10/>.
   Why: Repository discovery and summary ingestion feed directly into security conclusions, but no rule prevents instructions in those inputs from changing the analyst's task, omissions or tool authority. Evidence anchors and user validation check factual architecture/context, not the authority of embedded directives; discussing untrusted inputs to the application also does not protect the analyst consuming the repository. Integrity of the model under inspected-source influence is inside this security-analysis workflow, before the file boundary.
   Fix: in discovery and both prompt templates, make repository text, summaries and tool results non-authoritative evidence that cannot change the modeling contract, disclosure policy or permissions.
   Grep terms: `untrusted`, `ignore instructions`, `instruction hierarchy`, `prompt injection`; searched the skill and repository root with --max 10000. The target's untrusted-data question concerns application input handling; no analyst intake instruction was found, and uncalled siblings supply no coverage.

### Worth considering
2. **Preserve existing work when choosing the threat-model destination** [model+map+trace]
   Map node: agent.limit-agency — source: OWASP LLM06 <https://genai.owasp.org/llm-top-10/>.
   Why: The skill does constrain delivery to one basename-derived Markdown file, which is actual partial output-authority guidance. It does not decide what to do when that filename already exists, points through a symlink or belongs to another review; whether replacement is intended depends on the user's workspace.
   Fix: before saving, resolve the destination and its ownership/existing content, then use an explicit update, new-file or user-approved replacement decision.

3. **Let evidence determine counts instead of padding small models** [model+map+trace]
   Map node: design.risk-modeling — source: NIST SP 800-218, PW.1.1 <https://csrc.nist.gov/pubs/sp/800/218/final>; OWASP A06:2025 <https://owasp.org/Top10/2025/0x00_2025-Introduction/>.
   Why: The main workflow prefers few high-quality threats and the template forbids invented architecture, so there is direct protection against generic or speculative risk inflation. The same required contract asks for 5–10 abuse paths, at least two review paths and multiple criticality examples per level, which may not fit a tiny or low-risk repository.
   Fix: qualify the template minima with evidence/scope-based exceptions, allowing fewer or no applicable paths/examples and an explanation rather than manufactured items.

### Minor
4. **Retain the reviewed revision with the evidence anchors** [model+map+trace]
   Map node: agent.wrong-output — source: NIST AI 600-1, 2.2 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>; OWASP LLM09 <https://genai.owasp.org/llm-top-10/>.
   Why: Branch context and path/symbol anchors provide substantive evidence identity. A saved model still need not record an immutable revision or dirty-tree qualification, so later readers may inspect changed code when following the same path.
   Fix: in Scope and assumptions, record the reviewed revision/subpath and relevant local-change qualification.

5. **Check the generated diagram against its rendering contract** [model+map+trace]
   Map node: documentation.review-docs — source: O*NET 31.0, task 14647 <https://www.onetcenter.org/database.html>.
   Why: Conservative Mermaid syntax rules and a report-format check directly address diagram validity. No parse/render check of the actual emitted diagram is required, so those instructions do not themselves establish that a particular generated diagram renders cleanly.
   Fix: in the final quality check, validate the emitted Mermaid when a renderer/parser is available, or explicitly retain that check as unverified.
