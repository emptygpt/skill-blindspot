## Scope
- Tests and debugs local web applications using authored Python Playwright scripts, screenshots, rendered DOM and browser console logs.
- Includes static-file or dynamic-app reconnaissance, optional multi-server lifecycle helper, selector discovery and browser actions.
- Ends at executed browser automation and captured screenshots/logs with browser and helper-managed servers stopped.
- Does not implement app fixes, deploy, or operate a production testing service.

## Findings

### Needed
1. **Check the expected outcome, not just whether browser actions ran** [model+map+trace]
   Map node: testing.test-the-change, agent.wrong-output — source: ESCO, execute software tests <https://esco.ec.europa.eu>; O*NET 31.0, 15-1253.00 task 14639 <https://www.onetcenter.org/database.html>; NIST AI 600-1, 2.2 Confabulation <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: the description promises functionality verification, but the body and all examples stop at actions, screenshots or log capture without comparing results to an expected state. Folder/repository grep used `assert `, `expect(`, `expected` and `pass/fail`; no used file supplies an outcome oracle, so a successful click or script exit can be mistaken for a correct feature.
   Fix: in Reconnaissance-Then-Action and the examples, require an explicit expected result after each tested behaviour, evaluated by assertions or a stated visual comparison, and propagate mismatches as failures.

### Worth considering
2. **Choose scenarios before choosing selectors** [model+map]
   Map node: testing.plan-strategy, testing.regression-and-negative — source: O*NET 31.0, 15-1253.00 tasks 14638, 14645 and 14640 <https://www.onetcenter.org/database.html>.
   Why: the decision tree selects static/dynamic execution and server setup, not the behaviours to cover. Normal, empty, error and previously broken paths have no selection rule; the appropriate breadth depends on the user's requested test.
   Fix: before reconnaissance, derive a small scenario list and expected results from the task, including relevant failure and regression cases.
3. **Make state, data and browser coverage deliberate** [model+map]
   Map node: testing.environment-and-data — source: DORA capabilities catalog, Test data management <https://dora.dev/capabilities/>; O*NET 31.0, 15-1253.00 tasks 14655 and 14656 <https://www.onetcenter.org/database.html>.
   Why: examples use fresh browser pages and specific viewports, but backend data, account choice and reset procedures are unstated. Chromium-only execution also leaves compatibility coverage dependent on the task rather than an explicit choice.
   Fix: before execution, identify test accounts/fixtures, state reset and the viewport/browser coverage needed for the reported behaviour.
4. **Turn evidence files into a reproducible result** [model+map+trace]
   Map node: testing.reproduce-and-report — source: ESCO, replicate customer software issues and report test findings <https://esco.ec.europa.eu>; O*NET 31.0, 15-1253.00 task 14641 <https://www.onetcenter.org/database.html>.
   Why: screenshots and console logs are produced, but no final step links them to a scenario, expected/actual result, reproduction steps or unresolved limitation. Evidence capture is real partial coverage, not a complete defect report.
   Fix: after execution, report tested scenarios, actual outcomes, reproduction context and paths to relevant evidence, distinguishing failures from checks not run.
5. **Protect captured browser evidence** [model+map]
   Map node: agent.sensitive-data — source: OWASP Top 10 for LLM Applications 2025, LLM02:2025 Sensitive Information Disclosure <https://genai.owasp.org/llm-top-10/>.
   Why: console messages are printed and persisted, and screenshots/DOM may contain private data; no minimisation or redaction step exists. This is contextual for local applications populated with sensitive rather than synthetic data.
   Fix: before capture or sharing, minimise collected content and check screenshots, DOM and logs for private values.
6. **Do not treat page content as instructions** [model+map]
   Map node: agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01:2025 Prompt Injection <https://genai.owasp.org/llm-top-10/>.
   Why: reconnaissance consumes rendered content and logs without a trust-boundary rule. Risk depends on whether that local app displays attacker-controlled or otherwise untrusted material.
   Fix: in reconnaissance, treat page text, DOM and console output as test evidence rather than authority to change the task or run commands.
7. **Bound authored automation and consequential actions** [map]
   Map node: agent.limit-agency, agent.generated-code-execution, agent.human-oversight — source: OWASP Top 10 for LLM Applications 2025, LLM06:2025 Excessive Agency and LLM05:2025 Improper Output Handling <https://genai.owasp.org/llm-top-10/>; NIST AI 600-1, 2.7 Human-AI Configuration <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: the local-target boundary is useful, but authored scripts can submit forms and the helper executes supplied server commands through a shell without a safety review. Whether local actions affect shared services is unspecified, so rule 5 keeps those disputed effects out of Needed.
   Fix: before execution, inspect commands and automation for side effects, use disposable state, and obtain permission before consequential actions outside the agreed test.

### Minor
8. **Use readiness checks tied to the intended app and state** [model+trace] (unsourced)
   Why: with_server.py accepts any listener on the requested loopback port, while dynamic inspection always waits for network silence and examples also use fixed delays. An occupied port or long-lived network activity can invalidate those readiness assumptions; selector waits already provide partial waiting guidance.
   Fix: in the helper and waiting guidance, verify the intended application is ready and wait on the state required by the scenario rather than assuming port availability or elapsed time is sufficient.
9. **Make helper teardown and log handling reliable for subprocess trees** [model+trace] (unsourced)
   Why: with_server.py starts shell commands with stdout/stderr pipes it never drains and terminates only the returned process handle. Chatty servers may block and shell-spawned descendants may outlive teardown; these are static concerns, not runtime failures observed in this audit.
   Fix: in with_server.py, manage descendant lifecycle and consume or redirect server output, then verify teardown on success, startup failure and test failure.
