## Scope
- Security-focused differential review of existing PRs/commits/ranges against a baseline, with adaptive triage, history, test-presence and caller analysis.
- Includes called baseline/function context building and optional adversarial modeling: cited invariants, assumptions, reachability, scenarios and risk.
- Ends at a saved Markdown report with scope/confidence, findings, recommendations and user notification; optional formal report conversion is unavailable in this snapshot.
- Does not implement the proposed fix, execute a vulnerability-testing campaign, create/merge the PR, deploy or maintain the target. Reviewing an existing control does not imply implementing every security/UI/crypto node.

## Findings

### Needed
None. Main review safeguards are substantive; remaining scope/measurement issues have partial coverage, while workspace, trust and disclosure safeguards depend on input/workspace conditions.

### Worth considering
1. **Reconcile adaptive shortcuts with the final coverage promise** [model+map+trace]
   Map node: requirements.understand-request, requirements.consult-and-report, review.design-and-function, agent.human-oversight — source: O*NET 31.0, tasks 21662, 21665, 21673 <https://www.onetcenter.org/database.html>; Google Engineering Practices, Design/Functionality/Tests/Every Line <https://google.github.io/eng-practices/>; NIST AI 600-1, 2.7 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: The quality checklist says every changed file is analyzed, but examples permit skipping LOW files and restricting large changes to critical paths. Scope percentages and confidence already disclose limits; an explicit agreed exclusion list and independent review of critical claims would make the recommendation easier to rely on.
   Fix: at triage/final report, record excluded files/functions and unresolved questions, reconcile them with the checklist, and identify the human review still required.

2. **Separate heuristic counts and constructed scenarios from measured proof** [model+map+trace]
   Map node: agent.wrong-output — source: NIST AI 600-1, 2.2 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>; OWASP LLM09 <https://genai.owasp.org/llm-top-10/>.
   Why: Test-name searches and textual call counts supply useful leads, but do not establish runtime coverage or distinct reachable callers. Concrete scenarios, citations and reachability checks are real partial safeguards; numeric coverage/impact and PoC report fields still need a derivation and an observed-versus-unexecuted label.
   Fix: in methodology Phases 2–3 and reporting, retain count derivations, distinguish syntactic matches from semantic callers, and mark measured, estimated and unexecuted evidence.

3. **Pin review inputs and preserve the user's checkout** [model+map+trace]
   Map node: agent.limit-agency, agent.wrong-output — source: OWASP LLM06/LLM09 <https://genai.owasp.org/llm-top-10/>.
   Why: The workflow compares baseline/head and uses git history, but switches the working checkout without a clean-tree/identity preflight or an explicit read-only review boundary. This is conditional on workspace state and granted tools, not evidence that any user changes were overwritten.
   Fix: before baseline inspection, resolve immutable SHAs, preserve existing work and prefer Git-object reads or an isolated worktree; constrain any proposed exploit execution separately.

4. **Keep reviewed content from becoming operational authority** [model+map]
   Map node: agent.injected-instructions — source: OWASP LLM01 <https://genai.owasp.org/llm-top-10/>.
   Why: Source, comments, history and delegated analysis are consumed without an instruction/data boundary. Exploit reachability checks concern the target's attackers, not instructions aimed at the reviewing agent; exposure depends on who controls review inputs.
   Fix: at intake/delegation, require inspected content and subordinate records to remain evidence rather than tool/permission instructions.

5. **Apply a disclosure/redaction gate before writing reports** [model+map+trace]
   Map node: agent.sensitive-data — source: OWASP LLM02 <https://genai.owasp.org/llm-top-10/>; NIST AI 600-1, 2.4/2.9 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: Reports include source snippets, exploit details and concrete exposed-data descriptions, and may fall back to Desktop, temp or chat. Whether those contain secrets/private data is target-dependent; no minimisation or destination check is specified.
   Fix: before saving/notifying/converting, review sensitive values and exploit disclosure scope, and select an authorized persistent destination.

### Minor
6. **Carry failed function analyses into the dossier's omissions** [model+trace] (unsourced)
   Why: The called workflow filters falsy function records, returns ranked-below-cut functions as notAnalyzed, and separately logs analyzed/selected counts. A partially failed selection need not appear in that omission list, although top-level coverage/confidence requirements provide a chance to catch it.
   Fix: in audit-context.js synthesis/return handling, retain identities of selected analyses that failed and surface them alongside below-cut exclusions.

7. **Check report template and threshold boundaries** [model+trace] (unsourced)
   Why: The size/radius tables overlap at 200 files and 50 callers, and exact-size/percentage fields are requested without a final consistency check. These are reporting/triage ambiguities, not observed execution failures.
   Fix: in quick-reference/methodology tables and final checklist, define inclusive ranges and verify metric totals/links before notification.
