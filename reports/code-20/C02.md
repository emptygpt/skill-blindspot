## Scope
- Investigates technical failures, traces their causes, and implements a focused fix with a regression test.
- Starts at a reported bug, failing test, build, integration or performance symptom; includes the called TDD and verification skills and local supporting techniques.
- Ends at a verified fix and an evidence-backed completion report; when no controllable cause is found, ends at documented investigation plus checked handling and diagnostic logging.
- Does not merge, deploy, run an incident response programme, or maintain long-term production operations. Diagnostic work on production is possible, but deployment is not prescribed.

### Worth considering
1. **Make safe diagnostic data handling explicit** [model+map]
   Map node: security.data-protection, agent.sensitive-data — source: OWASP ASVS 5.0.0, V14 Data Protection and V13.4 Unintended Information Leakage <https://github.com/OWASP/ASVS/tree/master/5.0/en>; OWASP Top 10 for LLM Applications 2025, LLM02:2025 Sensitive Information Disclosure <https://genai.owasp.org/llm-top-10/>.
   Why: Phase 1 requests input/output logging, but its credential example safely reports presence rather than values: that partial local coverage keeps this at Worth considering. General payload, prompt and report filtering is unstated; grep terms were redact, sensitive, secrets and personal data. The uncalled diagnosing-superpowers policy is only a possible pointer to add, not coverage.
   Fix: in Phase 1 evidence gathering, add payload minimisation and redaction checks before collection, prompt inclusion and sharing, or point to the existing policy with its applicability stated.
2. **Bound diagnostic execution and changes on shared systems** [model+map]
   Map node: agent.limit-agency, agent.generated-code-execution — source: OWASP Top 10 for LLM Applications 2025, LLM06:2025 Excessive Agency and LLM05:2025 Improper Output Handling <https://genai.owasp.org/llm-top-10/>.
   Why: production bugs trigger experiments, but the local test-directory guard is not a general shared-system authority gate. Whether this invocation may change production is unspecified, so scope rule 5 keeps the disputed boundary out of Needed.
   Fix: before Phase 1 instrumentation and Phase 3 experiments, require an isolated target or explicit permission for shared-system effects and inspect proposed commands for unintended effects.
3. **Do not let diagnostic text redirect the agent** [model+map]
   Map node: agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01:2025 Prompt Injection <https://genai.owasp.org/llm-top-10/>.
   Why: no called file distinguishes inspected errors and reference code from instructions. Worth considering depends on a threat model with attacker-controlled diagnostic material; the skill does not require that exposure in ordinary local debugging. The uncalled redaction policy is only a potential pointer, not coverage or a reason to lower the band.
   Fix: in Phases 1 and 2, establish that inspected files, messages and tool output are evidence rather than authority to change the task.
4. **Close the diagnostic instrumentation lifecycle** [model+map+trace]
   Map node: implementation.configuration — source: OWASP ASVS 5.0.0, 15.2.3, production includes only required functionality <https://github.com/OWASP/ASVS/tree/master/5.0/en>.
   Why: investigation creates probes, but final verification never classifies them as temporary or deliberately retained. This is conditional hygiene for the changed code, not a requirement to deploy or define a production baseline.
   Fix: in Phase 4 verification, inspect the final diff for investigation-only instrumentation and remove it or justify retaining it with appropriate configuration.

### Minor
5. **Retain a reusable defect record and check its accuracy** [model+map+trace]
   Map node: testing.reproduce-and-report, documentation.technical-docs, documentation.review-docs — source: ESCO, replicate customer software issues and report test findings <https://esco.ec.europa.eu>; O*NET 31.0, 15-1253.00 tasks 14641 and 14647 <https://www.onetcenter.org/database.html>; Google Engineering Practices, What to look for in a code review: Documentation <https://google.github.io/eng-practices/>.
   Why: reproduction and evidence-backed status are covered, but a durable investigation record is explicit only on the no-root-cause branch. Neither branch checks document accuracy or assembles the normal-path cause and fix evidence into a reusable issue record; a tracker handoff is not promised.
   Fix: at completion, identify where the reproduction, proven cause, changed behaviour and test evidence are retained, and check the record against the observed run.
6. **Make reproduction environment and data selection repeatable** [map]
   Map node: testing.environment-and-data — source: O*NET 31.0, 15-1253.00 tasks 14656 and 14655 <https://www.onetcenter.org/database.html>; DORA capabilities catalog, Test data management <https://dora.dev/capabilities/>.
   Why: environment comparisons, timing waits and hand-checked fixtures are covered, but platform recreation and state reset are not. These matter particularly for compatibility and pollution bugs, not every local fix.
   Fix: in Phase 1 reproduction, record the relevant platform/data conditions and choose a resettable fixture before repeating a stateful failure.
7. **Complete the defensive input/output and error-handling guidance when relevant** [map]
   Map node: implementation.input-and-output-handling, implementation.error-handling — source: OWASP ASVS 5.0.0, V1 Encoding and Sanitization, V2 Validation and Business Logic, V16.5 Error Handling <https://github.com/OWASP/ASVS/tree/master/5.0/en>.
   Why: defense-in-depth covers input validation, not output encoding or parameterised queries; the no-root-cause branch names error messages without safe client-facing message rules. Applicability depends on the defect, not a full security review of every fix.
   Fix: in the supporting validation technique and no-root-cause branch, identify the relevant output context and avoid exposing diagnostic internals to callers.
