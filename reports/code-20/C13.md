## Scope
- Simplifies existing working code for clarity while preserving inputs, outputs, side effects, errors and ordering exactly.
- Includes history/caller/convention inspection, scoped incremental refactors, existing-test runs after each change, optional commits, and final build/lint/diff/readability checks.
- Ends at a behaviour-preserving, verified, reviewable refactor (committed when the optional per-change commit path is used), or rejection/reversion of a simplification that fails the checks.
- Does not add features, deploy, merge or undertake a production migration.

## Findings

### Needed
None. Exact behaviour preservation, explicit error/edge-case questions, mandatory unchanged-suite runs and reversion on failure supply partial safeguards even where the examples or verification method need strengthening. Uncalled sibling testing/review skills do not supply coverage.

### Worth considering
1. **Establish equivalence evidence when existing tests are weak** [model+map+trace]
   Map node: testing.plan-strategy, testing.unit-tests, testing.regression-and-negative, agent.wrong-output — source: O*NET 31.0, 15-1253.00 tasks 14638 and 14640 <https://www.onetcenter.org/database.html>; Google Engineering Practices, Tests and Small CLs <https://google.github.io/eng-practices/>; OWASP LLM09 <https://genai.owasp.org/llm-top-10/>.
   Why: The skill asks about edge/error behaviour and existing tests, then requires the suite to pass after every change without modifying it. It does not say how to proceed when those tests omit relevant behaviour or establish an unchanged-code baseline across all entry triggers; adding characterization checks before refactoring can strengthen proof without rewriting existing assertions.
   Fix: after Step 1, identify uncovered contracts, establish the baseline and add targeted characterization/differential checks where needed before transforming the code.
   Search check: `characterization`, `baseline`, `differential`, `coverage`, `synchronous` across skill and repository found no target instructions for that fallback; uncalled command/persona/sibling guidance is not coverage.

2. **Reconcile worked simplifications with the exact-preservation rule** [model+map+trace]
   Map node: implementation.modify-existing, agent.wrong-output — source: O*NET 31.0, 15-1252.00 task 21670 <https://www.onetcenter.org/database.html>; OWASP LLM09 <https://genai.owasp.org/llm-top-10/>.
   Why: The clarity example replaces an object whose entries contain the original item plus a count with a Map containing counts only, changing both container and values. Removing an async wrapper also needs a contract check because a dependency's synchronous throw becomes a direct throw instead of a rejected promise; Principle 1 and unchanged-suite checks remain real but incomplete counter-evidence.
   Fix: in Prefer Clarity and language-specific guidance, use semantically equivalent examples or state the required preconditions and show the equivalence checks, including error delivery.
   Static evidence: these are contrasts visible in the supplied examples, not executed reproductions; caller contracts and actual application impact are unverified.

3. **Bound bulk transforms and recovery to the agent's own edits** [model+map+trace]
   Map node: version-control.revert, agent.limit-agency, agent.generated-code-execution — source: GitHub Docs, Revert a pull request <https://docs.github.com/en/pull-requests>; OWASP LLM05 and LLM06 <https://genai.owasp.org/llm-top-10/>.
   Why: One-change-at-a-time, recent-change scope and reversion on failure reduce risk. The large-refactor automation rule has no preview/safety gate, and the revert instruction does not distinguish the simplifier's edit from pre-existing user changes.
   Fix: before editing or running a generated transform, record the starting diff and permitted paths, review/preview the transform and define rollback that preserves unrelated work.

4. **Make review and the equivalence handoff observable** [model+map+trace]
   Map node: version-control.commit-messages, version-control.change-description, agent.human-oversight — source: Conventional Commits 1.0.0 <https://www.conventionalcommits.org/en/v1.0.0/>; Google Engineering Practices, Writing good CL descriptions <https://google.github.io/eng-practices/>; NIST AI 600-1, 2.7 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: The final checklist asks whether a teammate/review agent would approve, and optional commits follow passing tests, but neither a real review nor a verification summary is required. Consumers cannot distinguish an independently reviewed refactor from the author's own expectation or see the limits of equivalence evidence.
   Fix: in final verification, report transformations, commands/results and known coverage limits; when committing, explain the intent, and require or explicitly defer independent review according to project policy.

5. **Keep inspected source/context separate from operational authority** [model+map]
   Map node: agent.injected-instructions — source: OWASP LLM01 <https://genai.owasp.org/llm-top-10/>.
   Why: The workflow reads supplied code, comments and history but supplies no rule for embedded instructions in that material. Exposure depends on the source and trust of the input; repository conventions are legitimate context, not blanket permission to override the user's refactoring scope.
   Fix: at context collection, distinguish authorized project rules from untrusted task data and refuse scope/tool changes carried only by inspected content.

6. **Minimise private context and reporting data** [model+map]
   Map node: agent.sensitive-data — source: OWASP LLM02 <https://genai.owasp.org/llm-top-10/>.
   Why: Source/history inspection can expose private implementation details or secrets, but the skill gives no minimisation/redaction rule. This depends on the material and agent environment, rather than an instruction to publish or disclose code.
   Fix: in Step 1 and the final handoff, limit collected/reported context and redact sensitive values while retaining enough information to explain the refactor.

### Minor
7. **Check downstream documentation references after renaming** [model+map+trace]
   Map node: documentation.technical-docs, documentation.review-docs — source: Google Engineering Practices, What to look for in a code review: Documentation <https://google.github.io/eng-practices/>.
   Why: Why-comments and project conventions are protected, but renaming symbols or removing wrappers can leave documentation/examples referring to old names even when runtime behaviour is unchanged.
   Fix: in final verification, check relevant documentation/examples and update references affected by the refactor.
