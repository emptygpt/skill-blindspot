## Scope
- Builds an MCP integration server for an external service, in Python or TypeScript.
- Starts with API/protocol research and endpoint selection; includes implementation, local transport setup, review, testing and read-only evaluation authoring and optional harness execution.
- Ends at an implemented, build/test-checked server and verified evaluation XML, or an evaluation report used to refine the server when the optional runner is used.
- Does not publish a package, deploy a production service, or maintain a live integration after delivery.

## Findings

### Needed
None. Local guides cover schema validation, authentication, safe-error principles, test assertions and answer verification; the remaining findings have partial coverage or depend on integration risk and the optional runner. Uncalled sibling skills supply no coverage.

### Worth considering
1. **Agree a consumer and security baseline before selecting tools** [model+map+trace]
   Map node: requirements.understand-request, requirements.technical-spec, requirements.consult-and-report, requirements.security-requirements, design.risk-modeling, design.decision-log, design.design-review, security.security-criteria — source: O*NET 31.0, 15-1252.00 task 21662 <https://www.onetcenter.org/database.html>; ESCO, define technical requirements <https://esco.ec.europa.eu>; NIST SP 800-218, PO.1.2, PW.1.1–PW.1.2 and PW.2 <https://csrc.nist.gov/pubs/sp/800/218/final>.
   Why: Phase 1 identifies endpoints, authentication and data models, but does not confirm consumer needs, acceptance limits or caller-specific risks with the requester. Generic security rules are useful partial coverage, not a recorded threat model or a design checkpoint before broad API exposure.
   Fix: in Phase 1.4, add a short agreed workflow/acceptance baseline, tool-permission threat review and recorded design checkpoint proportionate to the service.

2. **Extend smoke and retrieval evaluations into a repeatable test matrix** [model+map+trace]
   Map node: testing.plan-strategy, testing.unit-tests, testing.regression-and-negative, testing.environment-and-data, testing.security-testing, security.protect-environments-and-code — source: O*NET 31.0, 15-1253.00 tasks 14638, 14640, 14655–14656 <https://www.onetcenter.org/database.html>; Google Engineering Practices, Tests <https://google.github.io/eng-practices/>; NIST SP 800-218, PW.8 and PO.5 <https://csrc.nist.gov/pubs/sp/800/218/final>.
   Why: Best Practices names functional, integration, security and load testing, and the v2 guide implements a smoke client with invalid-input assertions. It does not supply unit-test seams, mutation/rollback fixtures, cross-transport/concurrent cases or an isolated test-account/data plan; read-only QA accuracy cannot establish those properties.
   Fix: in Phase 3.2, add a risk-based matrix covering helpers, empty/error/auth cases, supported transports and concurrent calls, with disposable data and explicit write-test boundaries.

3. **Carry the secret and safe-error rules through examples and evaluation artifacts** [model+map+trace]
   Map node: implementation.secrets, implementation.error-handling, security.data-protection, agent.sensitive-data — source: OWASP ASVS 5.0.0, V13.3–V13.4, V14 and V16.5 <https://github.com/OWASP/ASVS/tree/master/5.0/en>; OWASP Top 10 for LLM Applications 2025, LLM02 <https://genai.owasp.org/llm-top-10/>.
   Why: Environment-variable credentials and nonrevealing errors are explicit, but the Python guide also elicits an API key and logs queries, while the runner sends tool results to a model and records summaries without a filtering step. The v1 error helper can return an exception message, so the general rule is not consistently demonstrated.
   Fix: update the language examples and evaluation setup to use out-of-band credentials, sanitised error mappings and a private-data/redaction check before model calls or report delivery.

4. **Enforce the optional evaluator's authority and resource limits** [model+map+trace]
   Map node: agent.limit-agency, agent.generated-code-execution, agent.human-oversight — source: OWASP Top 10 for LLM Applications 2025, LLM05–LLM06 <https://genai.owasp.org/llm-top-10/>; NIST AI 600-1, 2.7 Human-AI Configuration <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: The evaluation guide repeatedly requires non-destructive calls and the workflow reviews generated server code before testing, so there is partial coverage. In the optional runner, run_evaluation lists every tool and agent_loop dispatches model-selected calls without a read-only allowlist, call budget or human gate; reachability is static from the documented runner entry point, not an observed unsafe execution.
   Fix: in Running Evaluations and its runner, require a least-privilege test identity, approved read-only tool set, reviewed server launch, task time/call budgets and explicit approval for any expanded authority.

5. **Separate fetched instructions from integration data** [model+map]
   Map node: agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01 Prompt Injection <https://genai.owasp.org/llm-top-10/>.
   Why: The workflow consumes web documentation and discovered service content without stating a trust boundary against embedded instructions. Worth considering depends on whether those inputs can be attacker-controlled; the audit did not establish that for a particular target service.
   Fix: in Phase 1 research and Phase 4 exploration, add a rule that fetched content is evidence, not authority to change the task, permissions or secret-handling rules.

6. **Verify acquired packages and copied code, not only SDK compatibility** [model+map]
   Map node: dependencies.choose-and-verify, dependencies.supply-chain, security.integrity, agent.suggested-dependencies — source: NIST SP 800-218, PW.4.1 and PW.4.4 <https://csrc.nist.gov/pubs/sp/800/218/final>; OWASP Top 10:2025, A03 and A08 <https://owasp.org/Top10/2025/0x00_2025-Introduction/>; OWASP Top 10 for LLM Applications 2025, LLM03 <https://genai.owasp.org/llm-top-10/>.
   Why: Official SDK pointers, explicit package names and v1/v2 selection provide partial provenance and compatibility guidance. There is no dependency-change review, package authenticity check or integrity check before installing tools or running the suggested latest codemod.
   Fix: in project setup and the migration subsection, add source/version verification and dependency-diff review before acquiring or executing components.

7. **Make review cover contracts and findings, not just style and compilation** [map]
   Map node: review.standard, review.design-and-function, review.analysis-tools — source: Google Engineering Practices, The Standard of Code Review and What to look for: Design, Functionality, Tests, Every Line <https://google.github.io/eng-practices/>; NIST SP 800-218, PW.7 <https://csrc.nist.gov/pubs/sp/800/218/final>.
   Why: Phase 3.1 checks duplication, errors, types and descriptions, and the language checklists cover several behavioural contracts. There is no explicit requirement to reconcile every implemented tool with the agreed plan or record and resolve analysis/review findings.
   Fix: extend Phase 3.1 with plan-to-tool/test reconciliation and disposition of compiler, analysis and review findings before evaluation.

8. **Finish the configuration and documentation handoff** [map+trace]
   Map node: documentation.review-docs, documentation.admin-settings, documentation.config-and-architecture — source: O*NET 31.0, 15-1253.00 task 14647 <https://www.onetcenter.org/database.html>; NIST SP 800-218, PW.9.2 <https://csrc.nist.gov/pubs/sp/800/218/final>; OWASP ASVS 5.0.0, V13.1, V15.1 and V16.1 <https://github.com/OWASP/ASVS/tree/master/5.0/en>.
   Why: Best Practices requires working examples, permissions, security considerations and rate-limit documentation. It does not require checking those documents against the finished server or inventorying configuration defaults and the distinction between upstream and inbound authentication.
   Fix: at the Phase 3 handoff, require a checked README with launch/config defaults, caller/upstream permission boundaries, security-relevant logging and reproducible test instructions.

9. **Specify transport protection and protected security logs for remote use** [map]
   Map node: security.crypto-and-transport, security.logging-and-detection — source: OWASP ASVS 5.0.0, V12, V16.3 and V16.4 <https://github.com/OWASP/ASVS/tree/master/5.0/en>.
   Why: The guides give HTTPS API examples, trusted-certificate OAuth guidance, loopback binds and server-side security-error logging. They do not describe remote TLS termination or log access/retention/redaction; these details depend on the intended hosting environment rather than requiring deployment in this skill.
   Fix: in Best Practices, add implementation requirements and a handoff checklist for remote transport protection and protected, non-sensitive security events.

### Minor
10. **Use a small feasibility spike when the integration is uncertain** [model+map]
    Map node: design.prototype — source: ESCO, develop software prototype <https://esco.ec.europa.eu>.
    Why: The process moves from API research to the full implementation without a throwaway compatibility/authentication probe. A known API may not need one.
    Fix: in Phase 1.4, add an optional bounded spike when protocol, authentication or upstream behaviour is uncertain.

11. **Check component and generated-code licence obligations** [map]
    Map node: dependencies.licence-compliance, agent.generated-ip — source: OpenChain License Compliance Specification 2.1, 3.1.5 and 3.3.2 <https://github.com/OpenChain-Project/License-Compliance-Specification>; NIST AI 600-1, 2.10 Intellectual Property <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
    Why: The skill's own licence and links to SDK examples do not check obligations for packages or copied/generated server code. Redistribution is not prescribed, so its importance depends on downstream use.
    Fix: in project setup and code review, add a component/example licence and attribution check appropriate to the intended use.
