## Scope
- Reviews user-named files/diffs/components for exploitable vulnerabilities, researching data flow, upstream controls, configuration and framework behavior across the codebase.
- Includes context-selected security guides and the explicitly called Django access-control and GitHub Actions review routes; does not import uncalled siblings.

## Findings

### Needed
1. **Make inspected repository content non-authoritative for the reviewer** [model+map+trace]
   Map node: agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01 <https://genai.owasp.org/llm-top-10/>.
   Why: The agent must research the entire codebase, and the called GHA route explicitly reads potentially poisoned agent configuration, but no runtime rule keeps that inspected text from redirecting the reviewer. modern-threats.md's summarizer defenses and the GHA poisoning examples concern applications/workflows under review, not the authority of content entering this reviewer's own context; they do not perform part of that intake-boundary work. This is an integrity safeguard inside adversarial code review, not a request to implement new application defenses.
   Fix: in the initial research instructions and called-review handoff, designate inspected code/comments/configuration and delegated evidence as non-authoritative data that cannot change review scope, reporting rules or tool permissions.
   Grep terms: `untrusted`, `ignore instructions`, `instruction hierarchy`, `prompt injection`; searched the complete skill folder and repository root with --max 10000, then read the relevant modern-threats and called GHA examples. Uncalled siblings do not supply coverage.

### Worth considering
2. **Reconcile authenticated-path exclusions and Always Flag shortcuts with contextual review** [model+map+trace]
   Map node: design.risk-modeling, security.identity-and-access, agent.wrong-output — source: NIST SP 800-218, PW.1.1 <https://csrc.nist.gov/pubs/sp/800/218/final>; OWASP ASVS 5.0.0, V6–V10 <https://github.com/OWASP/ASVS/tree/master/5.0/en>; OWASP LLM09 <https://genai.owasp.org/llm-top-10/>.
   Why: The parent excludes paths requiring prior authentication, although its authorization guide and called Django investigation explicitly examine authenticated cross-user access. Those are real instructions for the same review work, so the gap is conflicting coverage, not absence; the context-first gates also conflict with unconditional pattern shortcuts. Python's exception for user-derived settings is further concrete coverage that should qualify the parent's blanket server-controlled-value rule.
   Fix: in Do Not Flag and Quick Patterns, make the traced principal/data provenance and context gates authoritative, with explicit exceptions for authenticated authorization failures and user-influenced settings.

3. **Record review coverage, unresolved context and the next human decision** [model+map+trace]
   Map node: requirements.understand-request, review.design-and-function, agent.human-oversight — source: O*NET 31.0, task 21662 <https://www.onetcenter.org/database.html>; Google Engineering Practices, What to look for in a code review <https://google.github.io/eng-practices/>; NIST AI 600-1, 2.7 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: User-specified scope, candidate-level research and verification questions are explicit, and the Django route already requests unreviewed areas. The general output does not retain the reviewed revision/surfaces, skipped paths or a human disposition for material unknowns, making an empty high-confidence list hard to distinguish from incomplete review.
   Fix: add a brief coverage/limitations block and specific context or manual-verification requests before a clean-result conclusion.

4. **Define a read-only default and an authorized exception for active validation** [model+map+trace]
   Map node: testing.security-testing, agent.limit-agency, agent.generated-code-execution — source: NIST SP 800-218, PW.8.2 <https://csrc.nist.gov/pubs/sp/800/218/final>; OWASP LLM05/LLM06 <https://genai.owasp.org/llm-top-10/>.
   Why: Tool names/report scope are bounded, but reference recipes include scanners, gadget payloads and resource-exhaustion cases while SPEC says dynamic tools are out of scope. Whether those recipes are background or executable review steps is a genuine boundary question, so this is not Needed; neither interpretation currently gives the reviewer a clear operational rule.
   Fix: in SKILL.md, reconcile the testing recipes with a static/read-only default and, if execution is intended, require authorized isolated targets, inspected commands, disposable credentials and resource limits.

5. **Apply the review-data policy before copying vulnerability evidence** [model+map+trace]
   Map node: agent.sensitive-data — source: OWASP LLM02 <https://genai.owasp.org/llm-top-10/>; NIST AI 600-1, 2.4/2.9 <https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>.
   Why: SPEC specifically forbids storing secrets/PII observed during review, which addresses part of this exact evidence-handling work rather than merely application logging. Runtime instructions still require vulnerable snippets and secret findings without carrying that policy into the report/redaction step.
   Fix: at runtime evidence capture and report generation, redact discovered values and unnecessary private identifiers while retaining the location and enough structure to verify the finding.
