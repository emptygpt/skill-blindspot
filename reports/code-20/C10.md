## Scope
- Prepares and executes a production launch of already implemented software, including readiness gates and supporting telemetry/configuration.
- Includes referenced Definition of Done, security/performance/accessibility checklists and observability guidance as launch gates, not unrelated new-feature workflows.
- Ends at verified staged production rollout, a week of full-rollout monitoring and feature-flag cleanup, or verified rollback with team notification.
- Does not discover/build the original feature or run an indefinite maintenance programme.

## Findings

### Needed
None. The linked readiness material supplies human deployment approval, security/privacy controls, telemetry validation and provenance checks; remaining findings have partial coverage or depend on the deployment architecture/input trust. Uncalled siblings are not coverage.

### Worth considering
1. **Tie launch and rollback to an identifiable, retained release artifact** [model+map+trace]
   Map node: release.build-release-run, release.deploy, release.archive-and-integrity, version-control.revert, maintenance.first-look — source: The Twelve-Factor App, V Build, release, run <https://12factor.net/>; DORA, Deployment automation <https://dora.dev/capabilities/>; NIST SP 800-218, PS.2–PS.3 <https://csrc.nist.gov/pubs/sp/800/218/final>; GitHub Docs, Revert a pull request <https://docs.github.com/en/pull-requests>; O*NET 31.0, task 14661 <https://www.onetcenter.org/database.html>.
   Why: The sequence builds, stages and deploys, but does not bind checks to one promoted artifact/configuration or retain the previous deployable release. Its rollback template equates reverting/pushing with deploying a previous version, which depends on an unstated delivery pipeline; linked signed-artifact/provenance guidance is partial coverage, not an archive procedure. Hold/investigate and dashboard checks give an initial signal, not a first-look configuration/log/code diagnostic procedure.
   Fix: before staging, record release/configuration identity and artifact retention, then specify actual deploy/recovery commands and first diagnostic evidence for held/failed deployments.

2. **Verify environment and data recovery, not just application health** [model+map+trace]
   Map node: implementation.data-migration, testing.environment-and-data, release.environment-parity, operations.admin-processes — source: DORA, Database change management and Test data management <https://dora.dev/capabilities/>; O*NET 31.0, 15-1253.00 tasks 14655–14656 <https://www.onetcenter.org/database.html>; The Twelve-Factor App, IX, X and XII <https://12factor.net/>.
   Why: The rollback plan requests a verified migration command and a decision about newly inserted data, and staging tests are mandatory. It does not establish representative staging state, reconciliation/restore checks or graceful draining of requests/workers; a healthy endpoint alone cannot demonstrate data recovery.
   Fix: extend Infrastructure and the rollback plan with relevant parity checks, rehearsed data recovery/reconciliation and one-off migration/drain procedures.

3. **Name deployment authority and document protected operational settings** [map+trace]
   Map node: review.owners-and-approval, security.protect-environments-and-code, security.logging-and-detection, documentation.admin-settings, documentation.config-and-architecture, agent.limit-agency — source: GitHub Docs, CODEOWNERS and branch protection <https://docs.github.com/en/pull-requests>; NIST SP 800-218, PO.5 and PW.9.2 <https://csrc.nist.gov/pubs/sp/800/218/final>; OWASP ASVS 5.0.0, V16.3–V16.4 <https://github.com/OWASP/ASVS/tree/master/5.0/en>.
   Why: DoD requires human approval and observability guidance supplies alert escalation, so neither approval nor on-call coverage is absent. Release decision ownership, production access separation, settings/defaults and protected log-sink access/retention remain unstated.
   Fix: in the pre-launch handoff, name the release decision maker and applicable reviewers, and link the production access, configuration/defaults and log-protection runbooks.

4. **Keep launch evidence from granting authority or exposing sensitive values** [model+map]
   Map node: agent.injected-instructions, agent.generated-code-execution, agent.sensitive-data — source: OWASP Top 10 for LLM Applications 2025, LLM01, LLM02 and LLM05 <https://genai.owasp.org/llm-top-10/>.
   Why: Dependency-script gates and code approval provide partial execution protection, but application-level LLM hardening is not a rule for the deploying agent's own log/runbook intake, generated recovery commands or reporting. This depends on operational input trust/sensitivity and execution privileges, not a demonstrated malicious artifact or data leak.
   Fix: before deployment/recovery execution and reporting, verify command origin, target and authority, treat inspected artifacts as data and minimise/redact sensitive evidence.

### Minor
5. **Make rollout decisions total when the baseline or metric is unavailable** [model+trace] (unsourced)
   Why: The decision table has no explicit no-data/zero-baseline rule and leaves exactly 0.1% new client errors outside its less-than/greater-than conditions. Linked observability guidance improves SLO justification, but does not resolve these particular table boundaries.
   Fix: in Rollout Decision Thresholds, define equality, insufficient traffic/missing telemetry and zero-baseline handling before allowing advancement.
