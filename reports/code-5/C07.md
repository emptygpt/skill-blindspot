## Scope
- tdd is a reference skill for the red-green loop: what a good test is, seams (where tests go), three anti-patterns, mocking rules, loop rules. It writes no files and drives no session; the `implement` skill drives it.
- It starts when a concrete behaviour is to be built or fixed test-first and ends at a passing test with minimal code. Refactoring is excluded on purpose and sent to code-review.
- It does not involve requirements, security, dependencies, release, operations or documentation.
- `GLOSSARY.md` named in SKILL.md is the target project's optional file ("if it exists"), so it is not a missing file of the skill.

## Findings

### Needed
1. **The loop never says to run the test, watch it fail for the right reason, and run the suite after green** [model+map+trace]
   Map node: testing.test-the-change, testing.automation, agent.wrong-output — source: ESCO, "execute software tests"; DORA capabilities catalog, "Test automation"; NIST AI 600-1, "2.2 Confabulation"
   Why: searched SKILL.md, mocking.md, tests.md, docs/engineering/tdd.md for run, fail, suite, regression. The only line is "Write the failing test first, then only enough code to pass it" (SKILL.md, Rules of the loop). Without running the test, red is assumed rather than observed, which is exactly how a tautological test slips through. The repo's own doc quotes an agent skipping "watch it fail for the right reason", a line the skill no longer contains.
   Fix: in "Rules of the loop", add one rule to run the new test and confirm it fails for the intended reason before writing code, and to run the wider suite after green.

### Worth considering
2. **Bug-fix path has no instruction** [model+map]
   Map node: testing.reproduce-and-report, maintenance.fix-defects — source: ESCO, "replicate customer software issues"; O*NET 15-1252.00 task 21670
   Why: the description says "fix bugs test-first", but the body has no case that reproduces the bug as the first failing test. The repo's diagnosing-bugs skill covers this (regression test before fix) but tdd does not point to it, so it is not Needed.
   Fix: add a short bug-fix line in "Rules of the loop" or a pointer to diagnosing-bugs.
3. **Edge, boundary and error cases within a seam** [map]
   Map node: testing.regression-and-negative — source: O*NET 15-1253.00 task 14640 (regression testing, negative testing)
   Why: "You can't test everything" is the only guidance; tests.md shows only happy-path examples, so negative cases are named nowhere.
   Fix: add to "Seams" or tests.md how to pick which failure cases belong to a seam.
4. **Test data, fixtures and isolation between tests** [map+model]
   Map node: testing.environment-and-data — source: DORA capabilities catalog, "Test data management"
   Why: mocking.md covers boundaries ("Databases (sometimes - prefer test DB)") but not how to build data or keep tests independent or deterministic beyond time/randomness.
   Fix: add a short section to tests.md.
5. **Seam confirmation has no fallback when no user is present** [trace]
   Why: "No test is written at an unconfirmed seam" and "confirm them with the user", yet `implement` runs tdd per ticket and may be unattended. A blocked run has no stated way forward (for example, use seams from the spec).
   Fix: in "Seams", say where seams come from when no one can answer.

### Minor
6. **Description promises red-green-refactor, body has no refactor** [trace]
   Why: description mentions "red-green-refactor"; Rules of the loop say refactoring "is not part of the loop". It is deliberate and the repo docs acknowledge it as an open issue, so only the trigger wording is inconsistent.
   Fix: note in the description or first paragraph that refactoring is handed to code-review.
