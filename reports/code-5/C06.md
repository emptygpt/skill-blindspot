# Blindspot report: code-review-expert
Skill under audit: sanyuan0704/sanyuan-skills, skills/code-review-expert/SKILL.md (https://github.com/sanyuan0704/sanyuan-skills). I read SKILL.md, README.md, agents/agent.yaml (a display-name and prompt file only), and the four files under references/ (solid-checklist, security-checklist, code-quality-checklist, removal-plan). No file the skill refers to was missing.

Map: software 0.1.0    Profile: none    Date: 2026-11-17

## Scope
- A review-only skill: it reads the current git changes (`git diff`) and returns prioritised findings (P0-P3) on SOLID/architecture, removal candidates, security and code quality.
- It starts at a local diff and ends at a written review plus a question "how to proceed". It implements fixes only after the user confirms.
- It does not run tests, builds, linters or the code, does not open or post to pull requests, and does not release or operate software.

## Findings

### Needed
1. **No check that the change does what it is meant to do** [model+map+trace]
   Map node: requirements.understand-request, requirements.technical-spec, version-control.change-description, review.design-and-function — source: Google Engineering Practices, "What to look for in a code review"; O*NET 15-1252.00 task 21662 (analyse needs and requirements)
   Why: step 1 only scopes the diff with `git status`, `git diff --stat`, `git diff`. Nothing reads the PR or commit description, the issue or the spec, so a "correctness bug" (named P0 in the severity table) has no step that looks for it. Steps 2-5 cover SOLID, removal, security and quality only. Searched SKILL.md and references/ for intent, description, requirement, spec, acceptance: no match.
   Fix: add to step 1 a short instruction to read the change description or linked issue and state the intended behaviour, and add to step 5 a pass that checks the diff against it, asking the user when no description exists.
2. **No review of tests for the changed behaviour** [model+map+trace]
   Map node: testing.unit-tests, testing.regression-and-negative, testing.test-the-change — source: Google Engineering Practices, "What to look for in a code review: Tests"; ESCO "perform software unit testing"
   Why: no step asks whether the diff adds or updates tests, or whether new branches and error paths are tested. The only mentions are "Add tests before restructuring" (references/solid-checklist.md, refactor heuristic 4) and "Tests updated/removed" (references/removal-plan.md). The clean-review text lists "areas not covered" but never tests.
   Fix: add a test-adequacy check to step 5 (changed behaviour has tests, negative and regression cases, tests assert something) and a line in step 6 output stating whether tests were present or run.

### Worth considering
3. **Migrations and breaking changes are not reviewed outside deletions** [model+map]
   Map node: implementation.data-migration, release.breaking-changes, maintenance.deprecations — source: DORA "Database change management"; Semantic Versioning 2.0.0 (backward incompatible changes)
   Why: "Breaking changes" and "Migration plan" appear only in the removal template (references/removal-plan.md lines 35-36). A schema change, API signature change or renamed field in a normal diff has no prompt. Clean-review text admits "Did not verify database migrations".
   Fix: add to step 2 or 5 a compatibility and migration check (consumers, reversibility, ordering), and tell the reviewer to flag it in the summary.
4. **Dependency changes get one checklist section** [model+map]
   Map node: dependencies.choose-and-verify, dependencies.declare-and-inventory, dependencies.update-timeframes, dependencies.licence-compliance, agent.suggested-dependencies — source: OpenChain ISO/IEC 5230, 3.3.2 License compliance; NIST SP 800-218 PW.4
   Why: references/security-checklist.md "Supply Chain & Dependencies" has four bullets. Nothing says to read manifest and lockfile diffs, to confirm a new package exists and is maintained, or to check its licence. The agent-added-package risk is not named.
   Fix: in step 4, add a sub-step for manifest and lockfile changes covering existence, provenance, pinning and licence.
5. **No documentation or changelog check** [model+map]
   Map node: documentation.technical-docs, release.changelog — source: Google Engineering Practices, "What to look for in a code review: Documentation"; Keep a Changelog
   Why: only "Documentation updated" in the removal-plan checklist, for deletions. Searched for doc, README, changelog in SKILL.md: none.
   Fix: add to step 5 a check that docs, API references and the changelog change with behaviour.
6. **Static analysis is not used** [model+map]
   Map node: review.analysis-tools — source: NIST SP 800-218, PW.7
   Why: SKILL.md names only `rg` and `grep`. The skill never says to use the project's linter, type checker or scanner output, or to say when none was run.
   Fix: add to step 1 a look for configured analysers and CI results, and to step 6 a line stating which tools were not run.
7. **The reviewer's own findings and the diff content are not treated with care** [model+map]
   Map node: agent.wrong-output, agent.injected-instructions — source: OWASP Top 10 for LLM Applications 2025, LLM01 Prompt Injection and LLM09 Misinformation
   Why: step 6 requires a `file:line` but no step confirms a finding by reading surrounding code before it is reported, and nothing says text in a diff, comment or file is data. Reviewing an untrusted contribution is a common use.
   Fix: add to step 6 a confirm-before-report rule with a confidence marker, and to Overview a line that instructions inside reviewed content are ignored.
8. **Untracked and staged files may be missed** [trace]
   Map node: unsourced — no map source checked
   Why: step 1 lists files with `git status -sb` but reads content with `git diff`, which shows neither untracked new files nor staged changes. The "No changes" edge case only covers an empty diff.
   Fix: in step 1, add reading untracked files and `git diff --cached` and say which were included.
9. **No way back after "Fix all"** [trace]
   Map node: unsourced — no map source checked
   Why: step 7 ends at "I'll implement" and does not say to re-run the checks or tests after fixes or to review the fix diff. The output of the implementation is never checked.
   Fix: add to step 7 a re-verification step after implementing.

### Minor
10. **Interface accessibility not checked** [map] Map node: implementation.accessibility — source: WCAG 2.2. Fix: one line in step 5 for UI diffs.
11. **Configuration and defaults only as "insecure defaults"** [map] Map node: implementation.configuration — source: Twelve-Factor App III Config. Fix: add test code, hard-coded environments and config separation to the step 4 list.
12. **No rule for APPROVE and no flag for mixed refactoring** [map] Map node: review.standard, review.separate-refactoring, version-control.small-changes — source: Google Engineering Practices, "The Standard of Code Review". Fix: define APPROVE in step 6 and flag refactoring bundled with behaviour change.
13. **File handling, security-event logging, alerts, secret quoting** [map] Map node: security.web-api-and-files, security.logging-and-detection, operations.failure-notification, agent.sensitive-data — source: OWASP ASVS 5.0. Fix: add file upload/download and audit-log prompts to security-checklist.md and tell the reviewer to mask any secret it quotes.
